## 5. Hasil pengerjaan

**Yang dibangun:** `TestCaseFollowUpPanel` (panel "Tindak lanjut") dan `followUpNotes.ts` (catatan terisi dari Test Case dan hasil aktual); `TestCaseRunView` menampilkannya di bawah hasil Gagal/Terblokir yang tersimpan untuk QA yang ditugaskan; `TestCaseRunPage` memuat jejak delivery dan Bug yang sudah ada untuk hasil itu, lalu mengirim `createBug` (dengan `testResultId`) atau `updateTask` ke `changes_requested` dengan `reviewNotes`. Bila Bug sudah ada untuk hasil itu, panel hanya menampilkan keterangannya (tidak bisa kirim dua kali). Tanpa perubahan backend.

**Catatan BE-1:** test integrasi antrean yang sudah ada (`workQueueApiIntegration.test.ts`) sudah membuktikan kedua jalur: subtask `changes_requested` beserta `reviewNotes` muncul di `dev_blocked_work`, dan Bug yang ditugaskan muncul di `dev_bug_fix`. Karena itu tidak ada test backend baru.

**Pemeriksaan:** typecheck, eslint (tanpa error dan tanpa peringatan baru; 15 peringatan lama di file lain), build, `theme:check`, suite web 8 shard lulus; test baru: panel 6, halaman jalankan 1. UAT di Chrome Owner: panel tampil di bawah hasil Gagal dengan judul dan langkah reproduksi terisi, Developer harus dipilih bila ada lebih dari satu, "Minta perbaikan" memberi alasan bila tidak ada subtask Developer berstatus review. Kirim Bug sungguhan tidak dicoba di UAT agar tidak membuat Bug uji yang tidak bisa dihapus; jalur kirim teruji lewat test halaman.

**Deviasi dan catatan:**

- Panel ditempatkan di halaman jalankan (bukan halaman kerja QA), sesuai Bagian 3.
- Requirement pada Bug diambil dari Requirement pertama Test Case; Test Case dengan beberapa Requirement perlu pilihan Requirement di fase berikutnya.
- Daftar Developer penerima berasal dari subtask developer pada Requirement itu di jejak delivery.
